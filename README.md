# botmaker-cli

The **`botmaker`** command: everything a BotMaker plugin author does that is not writing the plugin — and,
under `bot`, everything a bot author does that is not writing the bot.

```bash
botmaker plugin new discord-notifier   # start a plugin project from the example plugin
cd discord-notifier
botmaker plugin validate               # the catalog's plugin checks, run locally
botmaker plugin run --project MyBot    # build it, add it to a bot, open Studio on the result
botmaker plugin publish                # release the next version and list it in the catalog
```

```bash
botmaker bot new farmbot                     # a blank bot project — no plugin, no SDK
botmaker bot new farmer --from alice/farmbot # …or somebody's published bot, linked to its author
cd farmbot
botmaker bot publish --repo me/farmbot
```

## Installing it

**Fedora / RHEL** — `botmaker` on your `PATH`, updated with the rest of the system:

```bash
sudo curl -fsSL -o /etc/yum.repos.d/botmaker.repo https://botmakerdev.github.io/botmaker-cli/botmaker.repo
sudo dnf install botmaker
```

**Debian / Ubuntu**:

```bash
sudo install -d -m 755 /etc/apt/keyrings
sudo curl -fsSL -o /etc/apt/keyrings/botmaker.asc https://botmakerdev.github.io/botmaker-cli/botmaker.asc
echo "deb [signed-by=/etc/apt/keyrings/botmaker.asc] https://botmakerdev.github.io/botmaker-cli/deb stable main" \
  | sudo tee /etc/apt/sources.list.d/botmaker.list
sudo apt-get update && sudo apt-get install botmaker
```

Both install one jar at `/usr/share/botmaker/` and a launcher at `/usr/bin/botmaker`, and need a **Java 25**
runtime. Maven is a *recommended* dependency rather than a required one: every verb that resolves a
coordinate shells out to your own `mvn`, and `botmaker bot new` / `bot publish` need none.

Both also install **tab completion**: `botmaker <TAB>` offers the nouns, `botmaker bot new --<TAB>` the
options. It is generated by `botmaker completion` at package time, from the same annotations that parse the
command line, so it cannot offer a verb the binary does not have.

**With JBang** (no install step, and it keeps itself up to date):

```bash
jbang botmaker@BotMakerDev plugin validate
```

**Without** — one jar, every OS, no JavaFX inside it:

```bash
curl -LO https://github.com/BotMakerDev/botmaker-cli/releases/latest/download/botmaker-cli-all.jar
java -jar botmaker-cli-all.jar plugin validate
```

Maven is required and is not bundled: this tool resolves what your own Maven resolves, using your own
settings, because the alternative is a tool that answers a different question from the one your build asks.

**`botmaker --help` and `botmaker <verb> --help` are the reference.** Every option below is described there
too, and there it is generated from the same fields that parse it — so where this file and `--help` ever
disagree, `--help` is right.

## Two nouns

`plugin` is what extends Studio; `bot` is what you build with it. Each is created, tried and published the
same way, and each spells its noun. The plugin verbs once sat at the top level (`botmaker new`, `validate`,
`run`, `publish`); typing one of those tells you where it went and runs nothing.

Three more verbs belong to the tool rather than to either noun: `doctor`, `completion`, and `release` — the
maintainer's cross-module release, run from the umbrella checkout.

## `botmaker plugin` — about a plugin

### `botmaker plugin new <artifact-id>`

Copies the example plugin, `botmaker-plugin-archetype`, and renames it: package and directories, the plugin's
name, the pom's coordinates (the plugin's identity) and the class its `botmaker.plugin` property names. The example is bundled in this jar as it was when this `botmaker` was released, so
the command needs no network; its pom names the plugin parent released with it, `botmaker-plugin-parent`, which
pins the contract and toolkit together (`--parent` names another). It carries **no templates of its own**: the shape has exactly one source of truth, a
plugin CI builds and tests, because three of the things it gets right (the dependency scopes) are wrong in ways
that produce no compile error.

```bash
botmaker plugin new discord-notifier --group com.example --plugin-name "Discord Notifier"
```

### `botmaker plugin validate [dir]`

The checks, in the same code the catalog's check runs on a pull request. The catalog runs the newest released
CLI, so until this version is released it runs that release's checks, which may be fewer than this list:

| check | passes when |
|---|---|
| `classpath` | the plugin's classpath resolves and every entry exists |
| `contract-links` | every contract member the plugin's classes link exists in this build's contract — the check a host makes before loading it |
| `loads` | a pom on the classpath sets `botmaker.plugin`, and the real loader constructs that plugin |
| `declared` | every pom naming a plugin names one a host loads (one per jar, a `public final` direct `DeclaredPlugin`, each coordinate once), and a catalog entry's plugin is the one with its coordinate |
| `palette` | `catalog().problems()` is empty and every entry names a real public member |
| `records` | every recorded-input method can be filled from a recording |
| `value-types` | every declared type answers a class and a fresh value, no class is declared by two plugins, and a component type takes its fresh value apart and puts it back |
| `managed` | every managed value is one a host can write as `public static T id() { return <expr>; }` |
| `editors` | every slot editor builds and every predicate answers without throwing |
| `pickers` | every declared type has an editor, its own or another plugin's |
| `pom-scopes` | `botmaker-studio-api` is `provided` or `compile`; `botmaker-plugin-toolkit` is not `provided` |
| `plugin-deps` | nothing the plugin's own code links is `optional` — `optional` means *not transitive*, so a host resolves the plugin without it |

`--coordinate G:A:V` validates a **published** artifact instead of your working copy. That is the one that
catches a plugin which builds on your machine and publishes a pom nobody else can resolve.

**A local pass is not a promise the pull request passes.** The catalog also asks that the published pom declare
the coordinate JitPack serves for the repository, which a local run cannot know.

**And a pass is never a safety claim.** A plugin runs arbitrary code inside Studio's process. Every check
here asks whether a plugin *works*.

### `botmaker plugin run`

`mvn install` into `~/.m2`, add the coordinate to one bot project's pom, launch Studio. **No tag is pushed
and nothing is released** — Maven checks `~/.m2` before JitPack, which is the same property the SDK has had
all along.

```bash
botmaker plugin run --project MyBot --umbrella ~/IdeaProjects/botmaker
botmaker plugin run --project MyBot --studio "/opt/BotMaker/bin/BotMaker"
```

It does **not** create a bot project. Composing one means composing its pom, and only the thing that knows
the whole plugin set can write the file that names them — that is Studio's job and it stays there.

### `botmaker plugin publish`

Run it in the plugin's folder, pushed to GitHub: it checks the plugin, tags and releases the next version,
waits for JitPack to build it, checks the jar, and opens the pull request on `botmaker-catalog` listing it. The
catalog's check runs on the pull request and merges it when it passes; nobody reviews it.

```bash
botmaker plugin publish                  # the next patch: v1.2.3 → v1.2.4 (v0.1.0 the first time)
botmaker plugin publish minor            # v1.2.3 → v1.3.0; `major` too
botmaker plugin publish --tag v2.0.0     # the version exactly; one released already is listed as it is
botmaker plugin publish --dry-run        # check and say what would be listed; tag nothing
botmaker plugin unpublish --repo me/discord-notifier [--release v1.2.3]   # the whole entry, or one release
botmaker plugin list                     # what catalog.json lists, with ranks
```

**You name nothing.** The repository is the folder's `origin` (`--repo` must agree with it), the plugin is the one the jar's pom
declares, and the catalog derives the name, the description, the contract version and the editor dependencies from
the pom at the release's commit. Each listed release is pinned: its commit, and the sha256 of the jar and pom
JitPack built, so nobody can change what was approved.

**A failure stops before what it would spoil.** A dirty tree or a failing check tags nothing. A JitPack build
that failed stops with its log and opens no pull request; that tag stays broken, so fix it and publish the next
version. A run that stopped after the release (no pull request yet) is finished by running it again: `HEAD`'s
released tag is listed, never bumped twice.

The pull request changes **one file**, `plugins/<owner>__<repo>.json`, appending the release; `catalog.json` is
generated by the catalog's own CI. The check report goes to stderr.

## `botmaker bot` — about a bot

The verbs above are all about a plugin. This is the other half: every **published bot** is a starting point —
a GitHub repository with a release and an entry in `botmaker-catalog`, which Studio's Browse Bots and New
Project list. There is no template kind (2026-10-23).

### `botmaker bot new <name>`

```bash
botmaker bot new farmbot                        # blank
botmaker bot new farmer --from alice/farmbot    # from a published bot
```

**Blank means blank**: a pom and one `main()` that prints a line. No SDK,
no plugin, no BotMaker API — that is what a project with no plugins installed looks like, and it is one step
from being a bot (**Project ▸ Plugins & Libraries…** in Studio). The repositories are declared, so that step needs
no hand-edited XML.

`--from` **clones** the bot at its newest GitHub Release (`--tag` for another), starts branch `main` there
and names the remote `original` — what Studio's Browse Bots does. Nothing is renamed, so the author's later
releases merge in (Studio's *Get vX.Y*), and the remote is the only record of where it came from. A bot runs
its author's code on your computer: read it before you run it.

### `botmaker bot publish`, `unpublish`, `list`

```bash
botmaker bot publish [patch|minor|major]            # in the bot's folder; --tag, --dry-run as for a plugin
botmaker bot unpublish --repo me/farmbot [--release v1.0.0]
botmaker bot list
```

`publish` works like `plugin publish`, in the bot's folder: it checks that the pom declares a catalog plugin at a
released version, that the bot compiles and that a class holds `main` (a dirty tree is refused), then pushes,
tags, releases and opens the catalog's pull request appending the release to `bots/<owner>__<repo>.json`. A folder
with no `origin` gets its repository created, named after the folder (`--repo` names another), and one that is
not a git repository yet is initialised and committed. The description and the topics are the repository's own,
read by the catalog. `unpublish` opens the pull request removing the entry, or one release of it, and keeps the
repository; `list` prints what `catalog.json` lists, with ranks.

## `botmaker doctor` — the tools everything else needs

```bash
$ botmaker doctor
ok    java      25.0.1 (Eclipse Adoptium)
ok    maven     Apache Maven 3.9.11  [./mvnw]
warn  gh        not installed — `plugin publish`, `bot publish` and `unpublish` need it
warn  studio    $BOTMAKER_STUDIO not set — `plugin run` needs --studio or --umbrella
```

Every verb already reports the tool it is missing — at the moment it is needed, which is halfway through
the first real use. This asks the whole set at once, reaches no network, changes nothing, and is the natural
thing to paste into a bug report. Exit 1 only if something **required** is missing; `gh` and Studio are
warnings, because only publishing needs `gh` and `--umbrella` is a real answer.

Which Maven it names is the one the other verbs will run (`./mvnw` beats `$MAVEN_HOME` beats `PATH`) — the
same code, not a second implementation of that precedence.

## `botmaker completion` — tab completion

The rpm and the deb install it; for the jar, or to try it in this shell only:

```bash
source <(botmaker completion)                          # bash
autoload -U +X compinit bashcompinit && compinit && bashcompinit && source <(botmaker completion)   # zsh
```

One script for both shells, because picocli emits bash and zsh runs it through `bashcompinit`. There is no
committed completion file: a hand-written one is a third statement of what the options are — beside the
parser and the usage text — and the one that fails silently, by quietly not offering a verb somebody added.

## `botmaker release` — the cross-module release

```bash
botmaker release --umbrella ~/IdeaProjects/botmaker --studio-api 0.6.0          # preview: decides, runs the gates
botmaker release --umbrella ~/IdeaProjects/botmaker --studio-api 0.6.0 --execute
```

The maintainer's tool, and the one implementation behind the umbrella's `release.sh` and the dashboard's
Release tab. It previews unless `--execute` is passed. Each module flag takes `x.y.z` or
`patch|minor|major`; `--why` also says why each forced module is in the release. The umbrella's `README.md` describes forcing and the
gates.

## Using it as a library

The main artifact is a **library**, and the executable jar is the `all` classifier. It holds two packages
other repositories call: `com.botmaker.cli.validate` — the author's `botmaker plugin validate` and the
catalog's check run the same code, so a submission never fails for a reason its author could not have seen —
`com.botmaker.cli.catalog`, the catalog's check, merge policy and index, and `com.botmaker.cli.release`, which
the dashboard runs in-process.

```xml
<dependency>
    <groupId>com.github.BotMakerDev</groupId>
    <artifactId>botmaker-cli</artifactId>
    <version><!-- latest tag: https://github.com/BotMakerDev/botmaker-cli/tags --></version>
</dependency>
```

```java
List<CheckResult> results = PluginValidator.validate(subject);
if (!PluginValidator.passed(results)) { … }
```

The package prints nothing, spawns nothing and reaches no network: it is handed resolved facts. Resolving
them is `com.botmaker.cli.Subjects`, and that is where Maven lives.

## Building

```bash
mvn test        # CommandLineTest, PomsTest, PluginValidatorTest, RegistryTest, BundledTest
mvn install     # com.github.BotMakerDev:botmaker-cli at the pom's main -SNAPSHOT, plus the -all jar
java -jar "$(ls -1t target/botmaker-cli-*-all.jar | head -1)" --help
```

The `-all` jar carries the version in its name because nothing renames it — a `<finalName>` would have
renamed only the *main* artifact and left the pair spelled two different ways. The release renames the asset
once, on the way out (`jreleaser.yml`), so the download URL above stays stable.

Published through JitPack, which serves each git tag under `com.github.BotMakerDev`. Releases are cut from the
umbrella only, with `--cli <version>` plus the downstream it forces (dashboard); `/release-check` names it.
